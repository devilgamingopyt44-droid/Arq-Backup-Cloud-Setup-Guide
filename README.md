## 🔍 What This Project Actually Is

Arq Vault Companion 2026 is a **wrapper, guide, and configuration accelerator** for cloud backup workflows on modern Windows systems. It does not attempt to reinvent the storage engine. Instead, it focuses on the *human layer* of backup — the parts that actually decide whether your archive survives the year:

- Choosing which folders deserve protection.
- Deciding how often snapshots should be taken.
- Selecting cloud destinations that suit your budget and jurisdiction.
- Understanding what "restore" really looks like before you need it.

Think of it as the **navigation system** for a well-engineered vehicle. The engine exists separately; this project makes sure you know where you are going, how long it will take, and what to do when the road forks.

## 💡 Why a Companion Instead of Just an Installer

An installer drops software onto a machine. A companion *teaches the machine what to do with it*.

Backup is one of those disciplines where the tooling is rarely the bottleneck — the bottleneck is the human sitting in front of it. Users skip configuration. They forget schedules. They point archives at drives that get unplugged. They assume "it's been running for months" when it quietly stopped in week two.

Arq Vault Companion 2026 exists to close that gap with:

- Plain-language configuration templates.
- Sanity checks before the first snapshot begins.
- A setup wizard that reads like a checklist, not a legal document.
- Documentation written for humans arriving from a search engine, not from a man page.

## ☁️ Cloud Targets and Storage Philosophy

This project is deliberately **provider-agnostic**. You choose where your data lives, and the companion accommodates the choice. Commonly used destinations include:

- Object storage buckets from major cloud vendors.
- Self-hosted storage servers behind your own domain.
- NAS devices exposed over encrypted tunnels.
- External drives rotated on a weekly schedule.

There is no bundled storage account, no intermediary relay, and no mandatory account creation. Your bytes travel from your machine to your destination — nowhere else.

The philosophical stance is simple: *backup infrastructure should be boring, owned, and auditable*. Anything that adds surprise steps violates that principle.

## 🚀 The Setup Journey, Step by Step

The recommended path from zero to first snapshot runs through seven phases.

**Phase 1 — Retrieval.** Obtain the distribution bundle using the macro above.

**Phase 2 — Unpacking.** Extract the archive into a directory you control. Avoid system directories and paths containing unusual characters.

**Phase 3 — Launch.** Open the application from the extracted folder using the primary executable. Windows SmartScreen may present a notice for newly distributed software; confirm the publisher prompt after verifying the file hash published in this repository.

**Phase 4 — Destination Selection.** Choose a cloud or local destination. The setup wizard offers presets for popular providers and a manual option for custom endpoints.

**Phase 5 — Scope Definition.** Select the folders you wish to protect. Templates are provided for common patterns: Documents, Pictures, Projects, Source Repositories, and a custom set.

**Phase 6 — Schedule and Retention.** Pick how often snapshots should occur and how far back history should be preserved. Defaults are calibrated for a typical home workstation.

**Phase 7 — Preflight and First Snapshot.** Run the preflight validator. It confirms credentials, connectivity, available space, and write permissions. When the validator passes, initiate the seed snapshot and let it run to completion — this first pass is typically the longest.

After the seed completes, subsequent snapshots are incremental and dramatically quicker.

## ⚙️ Configuration Reference

Configuration lives in a plain-text file that is easy to inspect, diff, and version-control. A minimal example follows, described in prose for clarity.

The top-level `profile` block names the configuration and records the schema version. The `destination` block specifies the provider type, endpoint, bucket name, and region. The `scope` block lists included and excluded paths using glob patterns. The `schedule` block defines the cadence using a cron-style expression. The `retention` block encodes the grandfather-father-son hierarchy with counts for daily, weekly, and monthly tiers. The `encryption` block records the key derivation method and the location of the key material — never inline the secret itself.

Because the file is plain text, it can be committed to a private repository for safe-keeping. Public repositories are discouraged for obvious reasons.

## 🗓️ Scheduling and Retention Policies

Schedules are expressed in cron syntax, which means anything from "every fifteen minutes during work hours" to "the first Sunday of each month at 3 AM" is representable. Three named presets ship out of the box:

- **Steady** — daily at a quiet hour, weekly deep verification.
- **Aggressive** — four times per day, hourly delta check.
- **Archivist** — weekly with long retention windows.

Retention policies decide how far back history survives. A common arrangement keeps seven daily snapshots, four weekly snapshots, and twelve monthly snapshots — a compact but resilient safety net. Additional tiers such as quarterly and yearly are supported for compliance-driven environments.

## 🛡️ Security Posture

Security is treated as a property of the whole pipeline, not a checkbox. Key considerations:

- **Client-side encryption** ensures data is unintelligible en route and at rest.
- **Key material** is expected to live in a secure store, not in the configuration file.
- **Network transport** uses modern TLS by default; older protocols are disabled.
- **Update integrity** is verified through published checksums in each release.

Users are encouraged to practice a restore at least once before trusting the pipeline with irreplaceable data. Untested backups are, statistically, not backups at all.

**Protecting a photography archive.** Include the Pictures and Lightroom catalogs, exclude raw previews cache, schedule a nightly incremental with weekly verification.

## 🧯 Troubleshooting Playbook

Signs the pipeline is unhappy usually fall into a small set of categories. The playbook below covers the most frequent arrivals on the support desk.

- **Credentials rejected.** Verify the access tokens and that they have not expired. Re-run the preflight validator.
- **Schedule skipped.** Confirm the operating system did not enter a low-power state during the window. Adjust the schedule or allow wake timers.
- **Seed snapshot slow.** Check upload throughput. Remember that the first snapshot is always the largest.
- **Restore mismatch.** Confirm you are browsing the snapshot timestamp you expected, not the live mirror.
- **Unexpected growth.** Inspect retention rules; older snapshots may not be expiring as you intended.

Deeper diagnostics are collected by the built-in logging subsystem and are safe to attach when contacting support.

## ❓ Frequently Asked Questions

**Does this require an account?** No. The companion operates with your own credentials to your own storage destination.

**Can I use multiple destinations?** Yes. Multiple profiles can run in parallel, each with its own scope and schedule.

**What happens if a snapshot fails midway?** The pipeline resumes from the last successfully committed chunk on the next run.

**Is the archive browsable without a full restore?** Yes. The restore browser offers a file-level view without materializing the whole archive.

**How do I migrate to a new machine?** Export the configuration, transfer the key material through a secure channel, and seed the new machine's cache from the destination.

**Are there any telemetry pings?** No. The companion does not phone home.
